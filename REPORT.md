## 2. Мета роботи

Пройти шлях від порожнього репозиторію до консольної програми, яку можна відтворювано
зібрати й запустити на Windows, macOS та Ubuntu.

Досягнуто:

- Maven-проєкт із Maven Wrapper, JUnit 5, SpotBugs і виконуваним JAR;
- програма читає CSV, перевіряє записи, обчислює чотири показники та формує звіт;
- GitHub Actions перевіряє `verify` на трьох ОС і публікує JAR як артефакт;
- робота спланована через GitHub Issues і здана через Pull Request; версію позначено тегом `v1.0.0`.

## 3. Постановка задачі

Формат запису (поля розділені `;`, кодування UTF-8):

```text
name:String; form:String; price:double; daysToExpire:int; prescription:boolean
```

Показники:

1. кількість коректних записів;
2. середня ціна препарату;
3. найменший термін до закінчення придатності (днів);
4. кількість рецептурних препаратів (`prescription = true`).

Правила перевірки: рівно 5 полів; `name` і `form` непорожні; `price` — число з крапкою ≥ 0;
`daysToExpire` — ціле ≥ 0; `prescription` — лише `true` або `false`. Хибний рядок не зупиняє
програму, а потрапляє до звіту з номером і причиною.

## 4. Структура програми

Пакет `ua.lpnu.kzp.pharmacy`:

| Клас                 | Відповідальність                                                     |
|----------------------|----------------------------------------------------------------------|
| `Main`               | розбір аргументів, коди завершення, запуск конвеєра                   |
| `FileReport`         | `Files.readAllLines`/`writeString` з явним UTF-8, створення каталогу  |
| `RecordProcessor`    | обхід рядків, видалення BOM, формування «Рядок N: причина»           |
| `MedicineLineParser` | `split(";", -1)`, перевірка кожного поля, нормалізація                |
| `ProcessingResult`   | незмінний результат: коректні записи + помилки                       |
| `PharmacyStatistics` | обчислення чотирьох показників                                       |
| `ReportFormatter`    | один текст звіту для консолі й файла (`Locale.ROOT`, `%n`)           |
| `BuildInfo`          | читання `version.properties`, підготовленого Maven                   |

Потік даних:

```text
args → Main → FileReport.readLines → RecordProcessor.process
     → (MedicineLineParser.parse для кожного рядка) → ProcessingResult
     → PharmacyStatistics → ReportFormatter.format → консоль + FileReport.writeReport
```

Читання, перевірка, обчислення та форматування розділені по різних класах. У ЛР2 масиви
`String[]` буде замінено класом `Medicine`, і зміни торкнуться лише парсера та статистики.

## 10. Академічна доброчесність

Під час виконання використано генеративний ШІ **Claude (Anthropic)** у ролях, описаних у
теці `ai/`: Менеджер, DevOps, Розробник, Валідатор, Документатор, Рецензент.

- **Менеджер**: розбиття вимог методички на GitHub Issues з критеріями готовності.
- **DevOps**: структура `pom.xml`, Maven Wrapper, SpotBugs, shade-плагін, workflow GitHub Actions.
- **Розробник**: пропозиції щодо структури класів і реалізації парсера.
- **Валідатор**: перелік крайових випадків (`NaN`, `Infinity`, `5d`, кома замість крапки,
  BOM, порожнє останнє поле, переповнення int, `Boolean.parseBoolean` для хибного тексту).
- **Документатор**: README, REPORT, javadoc.

Прийняті рекомендації та виправлені помилки:

- `Double.parseDouble` приймає `NaN`, `Infinity`, `5d`, тому додано перевірку регулярним виразом;
- `Boolean.parseBoolean("ні")` мовчки повертає `false`, тому використано явну перевірку;
- Блокнот Windows може додати BOM, тому його видаляємо з першого рядка;
- `InvalidPathException` є підкласом `IllegalArgumentException`, тому multi-catch не компілювався
  і його замінено одним `catch`;
- для `mvnw.cmd` задано CRLF у `.gitattributes`, бо cmd.exe некоректно виконує файли з LF.

Я переглянув увесь поданий код, розумію призначення кожного рядка та можу його пояснити.

## 11. Відповіді на контрольні питання

1. **Призначення pom.xml.** Це опис проєкту для Maven: координати (groupId, artifactId,
   version), версія Java, кодування, залежності та плагіни, які виконуються на фазах збірки.
2. **test, verify, package.** `test` компілює код і запускає модульні тести. `package` додатково
   збирає JAR. `verify` іде після `package` і запускає перевірки якості (у нас SpotBugs).
   Пізніша фаза завжди виконує всі попередні.
3. **Maven Wrapper.** Фіксує версію Maven у репозиторії та сам її завантажує, тому будь-хто
   (і CI) збирає проєкт тією самою версією без ручного встановлення.
4. **Метод main.** Це точка входу, з якої JVM починає виконання; він отримує аргументи
   командного рядка в `String[] args`.
5. **Примітив і String.** `int`, `double`, `boolean` зберігають саме значення й не можуть бути `null`.
   `String` — це незмінний об'єкт, змінна містить посилання на нього, а у класу є методи
   (`split`, `strip`…).
6. **Середнє в double.** Ділення `int / int` відкидає дробову частину (7 / 2 = 3). Тому потрібно
   ділити в `double`, щоб отримати 3.5.
7. **Integer.parseInt("abc").** Кидає `NumberFormatException`. Якщо її не обробити, програма
   аварійно завершиться.
8. **Чому не можна мовчки пропускати рядок.** Користувач не дізнається, що дані втрачено, і звіт
   буде хибним без жодного попередження. Тому потрібні номер рядка та причина.
9. **split(";", -1).** Від'ємний ліміт зберігає порожні поля в кінці: `"a;b;"` дає `["a","b",""]`,
   а без `-1` вийде `["a","b"]`, і замість «порожнє поле» отримаємо хибне «не та кількість полів».
10. **Path.of проти "data\\input.csv".** Зворотна скісна риска є роздільником лише у Windows.
    `Path.of("data", "input.csv")` сам підставляє роздільник поточної ОС.
11. **StandardCharsets.UTF_8.** Типове кодування залежить від ОС і локалі (на Windows це може бути
    cp1251), тоді кирилиця читається як «кракозябри». Явне UTF-8 дає однаковий результат усюди.
12. **%n і \n.** `%n` підставляє роздільник рядків поточної платформи (`\r\n` у Windows, `\n` в
    Unix), а `\n` завжди лише LF.
13. **Що перевіряти у варіанті 11.** Кількість полів (5), непорожні назва й форма, ціна — число з
    крапкою ≥ 0, термін — ціле ≥ 0, рецептурність — лише true/false, а також порожні рядки.
14. **Тести на середнє.** Набір із дробовим результатом (1 і 2 → 1.5) ловить цілочисельне ділення.
    Порожній набір ловить ділення на нуль або NaN, а один запис — помилку в лічильнику.
15. **Статичний аналізатор.** Шукає типові дефекти без запуску програми: можливий `null`,
    витік змінного стану, залежність від типового кодування тощо. Зупиняє збірку до того, як
    помилка потрапить у реліз.
16. **GitHub Actions.** Автоматично збирає й тестує кожен push і PR на чистих машинах трьох ОС,
    а потім публікує JAR як артефакт.
17. **Версія і номер збірки.** Версія (1.0.0) описує зміст релізу за SemVer, а номер збірки —
    конкретний запуск CI. За SemVer частина після `+` є метаданими збірки й не впливає на
    порівняння версій. Через крапку `1.0.0.42` виглядало б як інша версія.
18. **Issue на дефект.** Кроки відтворення, очікуваний і фактичний результати, а також
    середовище (ОС, версія).
19. **Розділ доброчесності.** Інструмент ШІ та ролі, запити, прийняті рекомендації, виправлені
    помилки та підтвердження, що я розумію весь код. Якщо ШІ не використовувався, це теж
    потрібно прямо написати.
20. **DevOps і Валідатор.** DevOps консультує щодо збірки, залежностей, аналізатора й CI.
    Валідатор шукає крайові випадки та оформлює дефекти, але сам код не виправляє.
21. **Найскладніший рядок.** Регулярний вираз `-?\d+(\.\d+)?` у `MedicineLineParser`. Він потрібен,
    бо `Double.parseDouble` приймає більше, ніж дозволяє формат варіанта (`NaN`, `1e3`, `5d`).
    Мінус свідомо дозволено у виразі, щоб окремо повідомити саме «від'ємна ціна».

## 12. Висновки

Створено кросплатформний Maven-проєкт «Аптека». Програма відтворювано збирається
однією командою на Windows, macOS і Ubuntu, перевіряє вхідні дані без аварійного завершення,
обчислює чотири показники та формує однаковий звіт у консолі й файлі. Інфраструктура
(Wrapper, JUnit 5, SpotBugs, shade, GitHub Actions, Issues/PR) готова для наступних робіт.

У ЛР2 рядкові масиви `String[]` буде замінено класом-сутністю `Medicine` з методом `fromCsv`.
Для підсумку з'явиться record `ExpiryPrescription`. Зовнішній формат звіту та наявні тести
мають залишитися без змін.
